# F4 — automatic owner notifications (policy, episodes, flood control)

Plan: [2026-11-03-F4-notification-policy.md](../superpowers/plans/2026-11-03-F4-notification-policy.md).

## What landed

- `crates/aq-server/src/notifications/policy.rs` — `Policy::observe(Event)` and
  `Policy::flush()`. Six event kinds with stable wire names:
  `task.failed_or_blocked`, `decision.needed`, `question.asked` (defined here for
  F5 to emit), `credential.invalid` (`Kind::from_failure_reason("credential_invalid")`,
  the C6b reason), `milestone.gate_ready`, `worker.offline`.
- **Milestone marker:** no v2 marker existed; F4 defines the Graph label
  `aq:milestone-gate` (`policy::MILESTONE_GATE_LABEL`). Subject = node ID.
- **Episodes** (`notification_episodes`, migration 58): key =
  `<kind>:<project_id>:<subject>` (subject = credential profile ID, task ID, node
  ID, worker ID, question ID). Open → one notification; further opens →
  `already_open`; resolve → `resolved`; reopen → generation+1 and one new
  notification. Operation and message IDs are derived (SHA-256 → RFC 9562 v8
  layout) from key + retained episode identity + generation, and the exact `SendRequest` is frozen in the
  policy transaction before it is submitted through `Service::enqueue`.
- **Replay:** `notification_policy_events` keys receipts by source event ID. A
  replay returns the original outcome and re-submits the identical frozen
  request; the store answers from its own receipt, so no second message,
  delivery or operation row is created (asserted on `operation_count`). A replay
  with different content is `notification_conflict`.
- **Flood control** (`notification_flood_windows`): per project/workspace 60 s
  window, at most 3 individual notifications; later episode openings in the
  window are `collapsed` (still open, so they stay silent until resolved). The
  notification runtime flushes closed windows every 5 s into **one** summary
  carrying the count and kinds (`"47 more events need attention…"`). Flush runs
  in its own spawned, 15 s-bounded producer task and never occupies dispatch capacity.
- **N4:** delivery outcomes never call the policy, so delivery failures cannot
  produce notifications about notifications. Summaries are bounded (title ≤ 240
  chars, control characters removed, subject ≤ 256 bytes, message ≤ store's 4096
  limit); no transcripts or private context. The link is the existing
  authenticated `/api/notifications/<id>` inspection URL. Mentions stay disabled
  (`Payload::wire`: `allowed_mentions.parse=[]`).
- **No route:** the store's `no_external_route` external state is returned
  unchanged; nothing claims external delivery.
- **Capacity:** 4096 episodes, 8192 source receipts, 1024 windows; refusal is
  `notification_capacity_exhausted`. Follow-up retention is described below.
- Recipient and actor are the earliest `owner` user; the per-destination
  isolation of AQ-24 dispatch is unchanged.
- Migration `0058_notification_policy.sql` (renumbered from 57 after `main` took 57 for observation source generations); `STATE_FORMAT_VERSION`,
  `READABLE_STATE_FORMATS` and Dockerfile `AQ_STATE_FORMAT` bumped to 58.

## Producer integration — steady-harbor-87.5.1

The five-second notification loop now reconciles durable public owner facts on
its dedicated pool, outside execution transactions and dispatch slots. Each
pass has a 15-second deadline; failures retry from retained rows. Source errors
produce a generic, rate-limited warning without transport errors or private text.

- D3 `agent_graph_outbox` has an independent `notification_observed` ACK and a
  frozen `notification_events` projection. Engine `delivered` remains owned by
  the playbook engine. Confirmed operations read Graph's authenticated, validated
  ready projection; labelled ready nodes open `milestone.gate_ready` episodes,
  and a complete projection resolves gates no longer ready. Unchanged gates do
  not consume new policy receipts. Work is bounded to 4096 ready nodes; larger
  or unavailable projections remain unacknowledged and retry. Freeze precedes
  observe, so a crash between observe and source ACK replays exact event IDs.
- `task.failed_or_blocked` observes latest retained result heads and D3 default
  settlements (`held` / `rework_required`). A later successful result resolves
  the episode. Graph's public task states have no failed/blocked variant;
  a process failure is an attention fact, never a fabricated Graph transition.
- Pending `human_decision_requests` joined to `review_subjects` open
  `decision.needed`; answer, cancellation or expiry resolves it. The observer
  reads only public IDs and request status, never encrypted subject contents.
- `worker.offline` uses the same heartbeat threshold as `/api/workers`, scoped
  to enabled project bindings and allowed nodes or configured worker groups.
  A current heartbeat or revocation resolves it. Repeated absence stays silent;
  a subsequent loss opens a new episode.
- All generated titles are the fixed text `Open AQ to review`; the policy adds
  only the kind and subject identity. Delivery never feeds back into producers.

**Two upstream gaps remain, as authorized by the supervisor:** no C6b failure
producer exists on available `calm-delta-18.10` refs, and the available
`steady-harbor-87.2*` refs contain F1b rather than F5. This change exposes tested
`Policy::observe_failure_reason(source, scope, profile_id, reason)` and
`Policy::observe_question(source, scope, decision_id, pending)` integration ports.
C6b must call the former with the retained `credential_invalid` event identity;
F5 must call the latter for pending and terminal transitions with distinct
retained event IDs. These are fixture-qualified consumer contracts, not claims
that the missing live producers are wired. No producer was invented.

**Retention:** migration 60 adds submission tracking, episode identities and
outbox fanout state. `retry_pending` submits up to 32 committed intents even
when the polling owner already sees its episode as open. Each GC pass removes
at most 512 rows per policy table older than seven days: submitted source
receipts, resolved episodes without pending intents, and empty or submitted
closed flood windows. Open episodes, unsubmitted intents and unflushed summaries
are protected. A collected episode later starts with a new identity, so resetting
its generation cannot reuse an older message/operation ID. The original caps
remain enforced; live protected state can still exhaust capacity.

This branch stacks F4 `aq/steady-harbor-87.5` (including `3a8d2b4b`) and D3
`aq/crisp-meadow-36.4` (`9415232b`), preserving both ancestries. D3's conflicting
migration 56 was reassigned to 59 because main already owns 56 (dashboard), 57
(observation sources), and F4 owns 58. Current state format is 60.

Follow-up verification uses disposable PostgreSQL and fake/no transport;
`notification_policy` covers all six kinds, replay, flood control, pending-intent
recovery, worker loss/regain/revocation, GC protection, fresh episode identity,
and recovery from all three policy caps. Additional retained-owner tests live in
`profiled_results/notification_sources.rs`; the D3 fanout replay test lives in
`playbook_bridge.rs`. Exact commands and results are recorded on the task.
