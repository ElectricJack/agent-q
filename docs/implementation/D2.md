# D2: repository onboarding and central Git remote credentials

Task `crisp-meadow-36.3`. Plan: [2026-11-04-d2-repository-onboarding.md](../superpowers/plans/2026-11-04-d2-repository-onboarding.md). Builds on D1b (`PublicationPolicy`) and the project binding route (`project_bindings`).

## What was built

### One owner operation (`crates/aq-server/src/repository_onboarding.rs`)

`onboard(state, actor, OnboardRequest) -> Value` is the single implementation. Two callers use it:

- the admin route `POST /api/repositories/onboard` (owner only, 128 KiB body cap), with `GET /api/repositories/onboard/{operation_id}` to read the stored state;
- the CLI `aq-server onboard-repository --vault <dir> --owner-email <email> --request <file|->` (`main.rs`). It loads the vault and the database the way `serve` does, resolves an owner by email, builds state through the new `aq_server::build_state` (extracted from `run`), and prints the same JSON. It exits 0 only when the result is `bound`. The CLI is a subcommand of the existing `aq-server` binary; nothing is installed as `aq` or `agent-queue`.

The request carries:

- `operation_id`, `project_id`, `repository_id`;
- `github: {owner, name}`;
- `transport: ssh | https`;
- `credential_profile?`;
- `default_branch?`, an owner override;
- `publication: {mode, wait_for_checks?}`;
- `template`, the remaining `ProjectBinding` fields.

The template may not set `project_id`, `repository_id`, `repository_binding_generation`, `repository_adapter_reference` or `publication`; doing so is a 400. The server fills in those fields.

The caller never supplies a URL, endpoint, token or command. The server builds the remote from `owner`/`name`: `ssh://git@github.com/{o}/{n}.git` or `https://github.com/{o}/{n}.git`. The GitHub API base and the credential profiles come only from vault `config.toml`:

```toml
[onboarding]
github_api_url = "https://api.github.com"   # default
[onboarding.credential_profiles.acme-deploy]
kind = "ssh_deploy_key"                      # or https_fine_grained_token
secret_file = "/vault/secrets/acme-deploy"
```

### Steps, persisted and resumable

Migration `0079_repository_onboarding.sql` adds the table `repository_onboardings`. It is keyed by `operation_id` and holds `actor_id`, a sha256 `request_digest`, `step` and `state jsonb`. Each step is written before the next one starts.

| Step reached | Work done to reach it |
|---|---|
| `started` | Validate the request and the binding template, including `ProjectBinding::validate` and `PublicationPolicy::validate`. Read GitHub metadata: `GET /repos/{o}/{n}` gives `default_branch`, and the owner override wins. `GET /repos/{o}/{n}/rules/branches/{b}` gives the signing rule. |
| `registered` | aq-git `repo.register` with `{identity, mode:"central", remote_url, allowed_refs:[target], allowed_targets:[target], credential_profile?}` at expected generation 0. The response must be central and SHA-1. |
| `synced` | aq-git `repo.sync {refs:[refs/heads/<default>]}` retains the base. The `base {ref, oid, observation_id}` is stored. |
| `checked` | aq-git `tree` on the retained head (top level, limit 1000) is pre-checked against the v1 profile. |
| `bound` | `project_bindings::put_binding` at expected revision 0 creates the project with `repository_adapter_reference = aq.git.configured`, the graph reference from the template (`aq.graph.configured`), the registered generation and the D1b publication policy targeting the default branch. |
| `refused` | A terminal, typed refusal. |

- **Response.** `{operation_id, step, disposition: bound|refused|incomplete, project_id, repository_id, remote_url, credential_profile, default_branch, repository_binding_generation, base, refusal?, error?, project?}`.
- **Replay.** Replaying a `bound` or `refused` operation returns the stored body byte for byte, and the GET endpoint returns the same body.
- **Transient failures.** A transient failure returns `incomplete` with `error{code, message, retry:true}` and keeps the step reached. Examples are aq-git being unavailable, GitHub being unreachable, or the binding route refusing because graph verification failed. Retrying the same `operation_id` resumes from that step.
- **aq-git operation ids.** Each aq-git mutation uses an operation id derived deterministically from the onboarding op and the step, so a resumed register is an aq-git idempotent retry.
- **Conflicts.** The same `operation_id` from another actor, or with a different request digest, gets 409.

### Typed refusals

`refusal = {code, reason, source, message}`:

| Condition | `code` | `reason` | `source` |
|---|---|---|---|
| `.gitattributes` at the head | `unsupported_repo_profile` | `gitattributes` | `precheck` |
| gitlink (mode `160000`) or `.gitmodules` | `unsupported_repo_profile` | `submodules` | `precheck` |
| `.lfsconfig` | `unsupported_repo_profile` | `lfs` | `precheck` |
| GitHub branch rule `required_signatures` | `unsupported_repo_profile` | `required_signing` | `precheck` |
| a `credential_profile` named while aq-git rejects it | `credential_profile_unavailable` | `credential_profile_unavailable` | `aq-git` |
| other aq-git `unsupported_feature` | `unsupported_repo_profile` | `unsupported_feature` | `aq-git` |
| register response not central or SHA-1 | `unsupported_repo_profile` | `object_format` | `aq-git` |
| `binding_conflict` on register | `repository_already_registered` | `binding_conflict` | `aq-git` |
| `invalid_request` on register, for example embedded HTTPS credentials | `invalid_repository` | `invalid_request` | `aq-git` |
| the default branch has no retained head | `unsupported_repo_profile` | `default_branch_absent` | `aq-git` |

## Profile fit (v1, pending J7)

| Property | v1 profile | How it is enforced |
|---|---|---|
| Object format | SHA-1 only | aq-git `repo.register` is SHA-1 only, and onboarding refuses a register response that is not `object_format: sha1` |
| History | complete | aq-git `repo.sync` always does a full fetch and has no shallow or partial mode (`unsupported_features` lists shallow and partial). Onboarding never requests either, so a shallow or partial retained base cannot arise |
| `.gitattributes` | refused | top-level pre-check. A nested `.gitattributes` is still refused later by aq-git's `no_attributes_v1` checkout with `unsupported_feature` |
| Submodules / gitlinks | refused | top-level pre-check on mode `160000` or `.gitmodules`. Nested gitlinks are refused by aq-git checkout |
| LFS | refused | top-level `.lfsconfig` pre-check. LFS pointers configured only through `.gitattributes` are caught by the attributes refusal |
| Required signing | refused | GitHub branch rules `required_signatures` |

J7 decides whether the profile widens (for example SHA-256, attributes or LFS). Until then the pre-check is deliberately conservative and top-level only, and aq-git's checkout remains the authority for the full tree.

## Credentials

- **Where they live.** The GitHub credential, a deploy key or a fine-grained token, lives only in a vault file named by `[onboarding.credential_profiles.<label>].secret_file`.
- **What gets persisted.** The request, the onboarding row, the binding JSON and every response hold only the profile **label**.
- **When the token is read.** aq-server reads a fine-grained token only to authenticate the GitHub metadata request, and holds it in memory for that request. The token is never written to the database, logged or sent to aq-git.
- **No sandbox exposure (SBX17).** No credential is passed into any sandbox. The onboarding module has no sandbox path at all.
- **Embedded URL credentials** cannot be supplied, because the caller provides no URL, and aq-git independently refuses them with `invalid_request`.
- **Profile checks.** A `credential_profile` must exist in the vault config, and its kind must match the transport (`ssh_deploy_key` with `ssh`, `https_fine_grained_token` with `https`). Otherwise the request gets a 400.
- **Known gap.** aq-git does not yet accept `credential_profile` on `repo.register`; it returns `unsupported_feature`. Onboarding therefore refuses with `credential_profile_unavailable` (`source: aq-git`). Public repositories onboard today without a profile. The cross-repo work is recorded as a task comment beginning `CROSS-REPO FOLLOW-UP (aq-git):`.

## Acceptance evidence

Tests are in `crates/aq-server/tests/repository_onboarding.rs`. They use a fake aq-git socket that records the register and sync params, and a fake GitHub API configured through `[onboarding].github_api_url`.

| Acceptance item | Test / evidence |
|---|---|
| One owner operation with an idempotent `operation_id` | `onboard_github_repo_creates_binding_and_retained_base`: a replay returns an identical body, register is received once, and GET returns the same body. `onboarding_resumes_after_partial_failure`: the same op with a changed body gets 409 |
| Registers the central aq-git binding | Same test: the register params are `mode: central`, `remote_url: ssh://git@github.com/acme/widgets.git`, `allowed_refs = allowed_targets = [refs/heads/trunk]`, with no credential field |
| `repo.sync` of the default branch (retained base) | Same test: the sync refs are `[refs/heads/trunk]`, and `base = {ref: refs/heads/trunk, oid: <head>, observation_id: obs-1}` |
| Default branch from GitHub or the owner override | `trunk` from fake GitHub metadata in the acceptance test. The override `release` wins in `onboarding_resumes_after_partial_failure` |
| Project created via the binding route (expected revision 0) | The acceptance test reads `GET /api/projects/{id}`: revision 1, `aq.git.configured`, `aq.graph.configured`, generation 1 |
| D1b publication policy | Same: `publication = {mode: fast_forward, target: refs/heads/trunk}` |
| Partial failure leaves explicit, resumable state | `onboarding_resumes_after_partial_failure`: graph verification fails → `incomplete`, `step: checked`, with `error.code`. The retry gives `bound` without a second register |

| Unsupported repository profile refused with a typed reason | `unsupported_repo_profile_refused_with_reason`: `gitattributes`, `submodules`, `lfs` and `required_signing` (`precheck`), and `credential_profile_unavailable` (`aq-git`). ## Limits and follow-ups

- The tree pre-check covers the top level only (limit 1000 entries). Deeper attributes and gitlinks are refused by aq-git at checkout rather than at onboarding.
- Onboarding steps are serialised process-wide by an in-process mutex, which is enough for a single aq-server. Running several replicas would need a row lock.
- Named credential profiles depend on the aq-git follow-up above.
