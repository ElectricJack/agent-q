Acceptance requires the node Bearer credential; a delegated permit cannot
accept an offer. Registration-v2 and re-adoption are likewise node-authenticated
operations. Delegated Prepare and renewal use `Authorization: Bearer <credential>`
with the opaque issued credential and an `aq-runner-channel` header containing
bare JSON `RunnerChannelIdentity`. That binding must equal the installed permit
binding. A node credential is never handed into the sandbox. Existing
node-authenticated Prepare remains available under its original contract.

The implemented transport has these additional rules:

- Each supplied `aq-permit-issuance`, `aq-permit-upgrade` and `aq-runner-channel`
  request header occurs exactly once and contains at most 8,192 bytes of JSON.
  Duplicate headers, invalid typed JSON and unknown schema fields are refused.
- Accept, Prepare and renewal require the existing `aq-delivery-nonce` UUID
  header. Prepare requires exactly one `Content-Type: application/json` header.
  Delegated renewal has a 16,384-byte request body limit.
- Issuance and upgrade responses include `aq-permit-revision` as a positive
  decimal integer: preparation issuance starts at 1 and execution upgrade
  advances to 2. Retain it for the first renewal request. Later revisions come
  from the typed renewal response body. This response header does not add a
  field to either frozen phase body.
- Issuance, upgrade and delegated renewal replies use `Cache-Control: no-store`.
  Credential-bearing response headers must be treated as secrets, including by
  proxies and logging systems.
- Issuance and upgrade correlate the typed operation ID and request digest with
  the native attempt, generation, boot, sandbox and phase profile. Their effects
  commit with native acceptance/grant. Exact replay redelivers the committed
  credential; changed operation content conflicts. Upgrade preserves the permit
  ID and credential while changing scope/expiry. Delegated Prepared requires its
  upgrade envelope, including an exact retry after upgrade.
- The frozen phase request/response bodies remain byte-compatible. The sibling
  permit envelopes travel only in the named headers. The dedicated planned
  registration/re-adoption routes and delegated renewal use `SandboxDocument`.

The planned routes and new-boot renewal still depend on the authority decision
below. The published transport mapping alone does not supply that authority.

## Resumed implementation

- Accepted offer and phase grant owners call permit issuance/upgrade inside
  their existing transactions. Operation digests and verifier-only response
  snapshots support exact credential redelivery. Changed envelope content
  conflicts. The frozen phase request/response bodies remain intact.
- `aq-permit-issuance` and `aq-permit-upgrade` carry the corresponding owner
  sibling envelopes as JSON request/response headers. Runner requests supply
  the opaque Bearer credential and JSON `aq-runner-channel` binding header.
  The supervisor provisionally accepted the published mapping above.
- Configure `[delegated_permits] key_file = "/private/path"` with a mode-0600
  regular file containing exactly 32 random bytes. Keep this key across server
  restart; no replacement is generated implicitly. Its HMAC-derived credentials
  are reproducible, while database records contain only SHA-256 verifiers.
- Each delegated effect transaction reloads node revocation, attempt ownership,
  current permit revision/scope/binding, node boot and native hot grant/deadline.
  It rechecks expiration using the injected clock after obtaining the locks.
- Material, source, artifact, Prepared, Started, observation, result/stopped,
  mailbox and terminal handlers now use scoped authentication. Decoded attempt
  references must match the permit. Native body validation still owns the other
  binding fields and effects. Node-only authentication continues to reject
  delegated credentials.
- Terminal candidate queries filter the attempt before LIMIT/cursor selection.
  Poll exclusion is per node/attempt channel and node wakeup reaches all its
  channels. Existing per-node byte, buffer and subscription accounting remains
  shared; no limits were multiplied by sandbox count.

rewritten or used to restart the hard deadline. Exact replay retains the committed
expiry/revision. Terminal cleanup recognizes an extended expiry only when the
retained renewal and current permit prove the same immutable phase origin.

   phase runtime/inventory/policy checks bind their facts to the original boot.
   The published re-adoption envelope does not define how those facts become

   `msg-efb3720fe4cf499093d7aa0e155cd40a` asks whether a separate delegated boot
   may renew against current grant/cancellation/hard deadline alone, or whether
   an owner-approved native authority transition must refresh the existing

2. The 0.3.0 validator permits `ReportResult` only under `Granted`, and denies
   all operations under `Ended`. Native stopped commits `Finished` plus verified
   `Stop::Stopped`; native results requires that stop first. The literal contract
   therefore cannot authorize the required stopped-to-result sequence or a
   stopped retry. A self-contained `CROSS-REPO FOLLOW-UP (aq-worker)` task comment
   requests published terminal-report semantics and vectors. Supervisor message
   `msg-eb56511b5cb84cbd9c8d6d36b74a2944` records both blockers. Finished native
   authority is not relabelled Granted to work around this.

Registration-v2, re-adoption, awaiting renewal, the named
reboot/restart acceptance tests, full route qualification, adversarial review
and acceptance publication remain outstanding. An authenticated handler is not proof

## Implemented

- `delegated_permits/model.rs`: owner-validated permit metadata, SHA-256 credential
  verifiers with constant-time comparison, revocation, and domain-separated HMAC
  credential reproduction from a separately supplied server key. The token is
  neither serialized in `PermitRecord` nor stored in PostgreSQL. A changed key
  refuses delivery instead of silently replacing an existing credential.
- `delegated_permits/storage.rs`: transaction-owned persistence, node/attempt
  ownership locks, operation digest replay/conflict, rollback and reconstruction.
  Concurrent exact operation retries retain a single original issuance.
  This helper is **not** an acceptance/grant authority: its caller must establish
  current boot, sandbox, generation, grant and deadline before insertion.
- Migration 46: immutable issuance records, monotonic revocation, retained replay
  evidence, and node-revocation/B3-cancellation triggers. Store startup checks that
  these triggers exist and are enabled. State format advances from 45 to 46.
- Six focused tests exercise metadata rejection, key mismatch, serialization,
  transaction rollback/reconnect, concurrent replay, actual B3 cancellation,
  node revocation, immutable history and startup refusal with a disabled guard.

The database test uses a disposable PostgreSQL database. Native grant/Started
setup uses the repository's synthetic native fixture; cancellation runs through
the actual administrative HTTP route. This is not provider or end-to-end runner
qualification. Reconnecting a pool proves storage reconstruction only; it is not
the required restart/renewal/result-deduplication scenario.
