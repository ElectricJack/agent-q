## Published transport contract

Supervisor message `msg-9f2a3821576a482f9b29694ddc81d127` provisionally accepts
this mapping and requests early publication for B6a2/B5b consumers. This is the
published server transport mapping for the pinned owner contract above; it is
not a declaration of complete B2 implementation or acceptance. Consumers should
pin the server commit containing this document together with the owner commit.

All schema names below refer to exact `#/$defs/<TypeName>` definitions in
[sandbox-v1.schema.json](../../vendor/aq-admission-0.3.2/artifacts/sandbox-v1.schema.json).
The corresponding owner vectors are in
[sandbox-v1.fixtures.json](../../vendor/aq-admission-0.3.2/artifacts/sandbox-v1.fixtures.json).
The schema root describes `SandboxDocument`, whose JSON representation is
`{"kind":"<tag>","body":<typed object>}`. Header envelopes contain the bare
typed object, without that wrapper. No locally extended owner schema is used.

| Method and route | Request | Response | Checkpoint status |
| --- | --- | --- | --- |
| `POST /v1/worker/profiled-v2/accept` | Existing nominal phase Accept body; optional `aq-permit-issuance` header containing `PermitIssuanceRequest` | Existing nominal AcceptedDelivery body; `aq-permit-issuance` containing `PermitIssuanceResponse` when issued | Implemented for frozen and refresh phase profiles |
| `POST /v1/worker/profiled-v2/prepare` | Existing nominal phase Prepare body; `aq-permit-upgrade` containing `PermitUpgradeRequest` for delegated Prepared | Existing nominal ExecutionDelivery body; `aq-permit-upgrade` containing `PermitUpgradeResponse` when upgraded | Implemented for frozen and refresh phase profiles |
| `POST /v1/worker/profiled/renew` | `SandboxDocument` tag `runner_renewal_request`, body `RunnerRenewalRequest` | `SandboxDocument` tag `runner_renewal_response`, body `RunnerRenewalResponse` | Same-boot and adopted-boot renewal implemented; pending registration returns awaiting re-adoption; legacy node renewal keeps its body contract |
| `POST /v2/worker/register` | `SandboxDocument` tag `register`, body `Registration` | `SandboxDocument` tag `registration_response`, body `RegistrationResponse` | Implemented under Option A |
| `POST /v2/worker/readopt` | `SandboxDocument` tag `readoption_request`, body `ReadoptionRequest` | `SandboxDocument` tag `readoption_response`, body `ReadoptionResponse` | Implemented under Option A |

Acceptance requires the node Bearer credential; a delegated permit cannot
accept an offer. Registration-v2 and re-adoption are likewise node-authenticated
operations. Delegated Prepare and renewal use `Authorization: Bearer <credential>`
with the opaque issued credential and an `aq-runner-channel` header containing
bare JSON `RunnerChannelIdentity`. That binding must equal the installed permit
binding. A node credential is never handed into the sandbox. Existing
node-authenticated Prepare remains available under its original contract.

The implemented transport has these additional rules:

- Each supplied `aq-permit-issuance`, `aq-permit-upgrade` and `aq-runner-channel`
  request header occurs exactly once and contains at most 8,192 bytes of JSON.
  Duplicate headers, invalid typed JSON and unknown schema fields are refused.
- Accept, Prepare and renewal require the existing `aq-delivery-nonce` UUID
  header. Prepare requires exactly one `Content-Type: application/json` header.
  Delegated renewal has a 16,384-byte request body limit.
- Issuance and upgrade responses include `aq-permit-revision` as a positive
  decimal integer: preparation issuance starts at 1 and execution upgrade
  advances to 2. Retain it for the first renewal request. Later revisions come
  from the typed renewal response body. This response header does not add a
  field to either frozen phase body.
- Issuance, upgrade and delegated renewal replies use `Cache-Control: no-store`.
  Credential-bearing response headers must be treated as secrets, including by
  proxies and logging systems.
- Issuance and upgrade correlate the typed operation ID and request digest with
  the native attempt, generation, boot, sandbox and phase profile. Their effects
  commit with native acceptance/grant. Exact replay redelivers the committed
  credential; changed operation content conflicts. Upgrade preserves the permit
  ID and credential while changing scope/expiry. Delegated Prepared requires its
  upgrade envelope, including an exact retry after upgrade.
- The frozen phase request/response bodies remain byte-compatible. The sibling
  permit envelopes travel only in the named headers. The dedicated
  registration/re-adoption routes and delegated renewal use `SandboxDocument`.

The registration route is shared with the existing fixture execution protocol.
A sandbox `kind` envelope selects the published owner type; the original bytes
are decoded with that type so duplicate fields remain detectable. Requests
without that envelope keep the existing fixture registration handler.

Register through v2 before permit issuance to retain the backend advertisement
with the grant. An earlier permit without that snapshot cannot be re-adopted.
Registration/readoption bodies are limited to 32,768 bytes; the typed registration
object is additionally limited to 16,384 bytes. Both replies use `no-store`.
Readoption retains the permit ID, channel ID, revision, issued time, expiry and
hard deadline. It changes the boot binding and rotates the opaque credential;
replace both the credential and binding before the next runner request. Keep the
installed revision for renewal. An awaiting reply has no delivery clock and must
not extend the runner's prior deadline.
