# C5a2: material leases bound to delegated permits

Task: `calm-delta-18.13`. Plan:
`docs/superpowers/plans/2026-11-04-c5a2-material-lease-permit-binding.md`.

## Change

- Migration `0076_material_lease_permit_binding.sql` adds a nullable
  `admission_material_leases.permit_id`, which references `delegated_permits`.
  A `BEFORE INSERT OR UPDATE` trigger enforces three rules:
  - The binding is set once. It can't change after being set; the trigger
    refuses with SQLSTATE 23514.
  - The permit must belong to the lease's admitted attempt and node.
  - A newly set binding can't name a permit that is already revoked.
- `delegated_permits::handoff::issue_locked` binds the attempt's admitted,
  unbound leases to the new preparation permit. It does this in the same
  accept transaction that inserts the leases and the permit. This includes
  rows mapped through `profiled_launch_materials`. `upgrade_locked` keeps the
  permit id, so the binding still holds for the execution scope.
- `profiled_execution::material_api::fetch` adds a check for a delegated
  caller, after the locked lease-row recheck. The lease's `permit_id` must equal
  the authenticated permit. The `delegated_permits` row (immutable issuance
  fields, mutable `revoked` flag) must exist for that permit, node and request
  attempt, and must not be revoked. That row is read `FOR SHARE`.
  If any check fails, the response is the existing uniform 409 refusal.
- Node-authenticated callers (no permit) skip the new check, so their behavior
  is unchanged. No wire types changed.

## Why a gen+1 permit is the red case

Preparation-scope `authenticate_runner` only checks that the permit's attempt
and generation match the preparation origin. A second permit for the same
attempt, with a new sandbox and grant generation, passes authentication and
`require_binding`. Before this change it received lease A's secret, with a
200 response. Accept-time issuance can't mint such a permit today, because the
vendored issuance check pins the accept operation and generation. So the test
builds it directly, as a defence-in-depth case: the lease, not issuance
policy, now decides which permit may read it.

## Evidence

`cargo test --locked -p aq-server --test profiled_material
lease_bound_to_permit_refuses_other_attempt` passes. The test asserts:

| Case | Result |
|---|---|
| Re-binding lease A to another permit | DB error |
| Binding lease B to attempt A's permit | DB error |
| Lease A, other-sandbox permit of the same attempt | 409 |
| Lease A with attempt B's binding, attempt B's permit | 409 |
| Lease A, attempt B's permit | 403 (`require_binding`) |
| Unbound lease B, attempt B's permit | 409 |
| Unbound lease B, node credential | 200 |
| Lease A, owning preparation-scoped permit | 200 with secret |
| Lease A, node credential | 200 |
| Lease A after the owning permit is revoked | not 200 |

The re-binding errors, the other-sandbox 409, the unbound-lease 409 and the
owner 200 depend on this change. The cross-binding 409 (the first lookup
filters on attempt), the 403 and the revocation refusal (authentication
rejects revoked permits) were already enforced. They are kept as regression
pins.

`delegated_permit_runtime::accept_issues_and_grant_atomically_upgrades_same_permit`
now asserts that a real accept with issuance binds every material lease of
the attempt to the issued permit. This covers the `issue_locked` UPDATE.

## Limits

- Legacy v1 `preparation.rs` leases are node-only and are never bound. A
  permit can't fetch them, which is intended: they have no permit.
- Revocation is already fenced at authentication, and the node row lock
  serializes revocation with delivery. The `FOR SHARE` read is a redundant
  recheck.
- There is no backfill. A permit fetch for a lease admitted before the
  migration gets 409, while the node path still works. In-flight preparations
  at deploy time fall back to the node path or re-prepare.
