Both acceptance tests are in `crates/aq-server/tests/profiled_results/questions.rs`. They use a real admitted attempt (`review_env`).

What `question_answer_resumes_waiting_attempt` asserts:
- Asking creates one pending `question` decision at revision `"1"`, with the task as its subject. An H4 wait is registered for it and is `pending`.
- Replaying the ask returns an identical response. The same `operation_id` with a different question gives `id_conflict` and creates nothing; exactly one decision row exists.
- An answer at the wrong revision gives `stale_revision`. An answer at revision 1 returns revision `"2"` with delivery `{"kind":"wait"}`.
- Replaying the answer returns an identical receipt. A different answer at revision 2 gives `id_conflict`.
- Two reconciler passes record exactly one `satisfied` outcome and one `ready` resume intent.
- `show` returns the answer. No mail is sent to a live waiting attempt.

What `question_after_attempt_ended_routes_to_continuation` asserts:
- The asking attempt's launch binding is revoked before the answer arrives.
- The answer's delivery is `task_mail`.
- Exactly one mailbox message is sent on the decision's thread. It has these properties:
  - It is addressed to the task, not a session.
  - Its sender is the `question_answer` system component.
  - Its body carries the answer.
  - Its `message_id` equals the receipt's.
- No session-addressed mail exists.

## How each requirement is met

- **Migration 0092** (`crates/aq-server/migrations/0092_question_decisions.sql`): the `question_decisions` table.
  - It holds one row per (attempt, operation): the question, its digest, and the subject revision `attempt:{attempt_id}:{generation}`.
  - It also holds the decision revision, the state (`pending` or `answered`) and the H4 `wait_id`.
  - CHECK constraints force the answer columns (answer, owner, operation, receipt digest, time, delivery) to be all set when answered and all null when pending.
  - A partial unique index on (answered_by, answer_operation_id) makes answer replay lookups exact.
- **Ask** (`agent_access::questions::ask`; `POST /v1/agent/questions`, capability `question.ask`):
  - The caller is authenticated with the per-attempt machine credential. Its scope comes from `waits::load_caller`.
  - The decision row and an H4 `HumanDecision` wait are inserted in one transaction, via `waits::register_locked`. The wait's IDs are UUIDv5 values derived from the decision ID. If the attempt already has an active wait, the whole ask is refused with `wait_conflict`.
  - Questions are limited to 4096 bytes. A replay by (attempt, operation) returns the stored view, and a different digest gives `id_conflict`.
- **Show** (`POST /v1/agent/questions/show`, capability `question.show`): returns the decision and, once answered, the answer and receipt digest. It is scoped to the caller's project, workspace and task.
- **Answer** (`questions::answer`, exposed as the G1b dashboard action `question.answer` in `questions/action.rs`):
  - Only the owner may answer, and the answer must target the exact `expected_revision`.
  - The row is locked `FOR UPDATE`.
  - A replay with the same owner, operation and text returns the stored receipt. Anything else on an answered decision gives `id_conflict`.
  - The receipt digest is a digest of the receipt JSON.
  - Discord replies and notification acknowledgments are never answers.
- **Delivery.** The answer path checks whether the asking attempt has ended. An attempt has ended if it no longer holds the task, has a cancellation, has a revoked launch binding, or has no attempt row at all.
  - **Live attempt:** delivery is `{"kind":"wait"}`. The H4 wait source (`waits/sources.rs`) falls back to `question_decisions` when no review decision matches. It checks the subject, subject revision, question digest and scope. The waiting attempt then wakes once through the normal outcome and resume intent.
  - **Ended attempt:** delivery is `{"kind":"task_mail","message_id"}`. One task-addressed message is sent in the same transaction, through `messaging::question_send_in_tx`, on thread = decision ID. The message ID is UUIDv5 of the answer operation, so the continuation can read it.
- **Notifications.** After commit, F4's `Policy::observe_question` is called on a best-effort basis: on open (pending) and on answer. It carries only the decision ID and scope, never the question or the answer text.
- **Published contract.** `protocol/agent-questions/v1/{routes.json, README.md}`. The README covers the routes, error codes, replay rules and delivery. The regenerated `protocol/dashboard-actions/v1/schema.json` includes `question.answer`.
- **Errors.** `id_conflict`, `stale_revision` and `wait_conflict` map to HTTP 409, together with the existing `stale_generation`.
