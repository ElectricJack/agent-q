## What shipped

### Coding policy (`crates/aq-server/src/playbooks/coding.rs`)

`CodingPolicy { implementer_family, reviewer_family, checks, max_repairs }`.
`build()` seals four artifacts with `Artifact::seal` and verifies them. They
use only commands and events from the pinned Host7 catalog (`CatalogProfile::Host7`).
Each artifact's registry is pruned to the contracts it uses.

| artifact | role |
|---|---|
| `aq.coding.work` | `work.ensure` → `accepted` / `changes_requested` / `escalated`. Handles both the sync path (`completed`) and the async path (`accepted`, then waits for `aq.operation.updated`). |
| `aq.coding.check` | `check.request` → `passed` / `failed` / `escalated`. Handles both the sync path and the async path (waits for `aq.check.receipted`). |
| `aq.coding.attempt` | Runs these steps in order: work (implementation or repair), `candidate.prepare`, every required check on the prepared candidate, `work.ensure kind=review` with the reviewer-family context, then `candidate.publish` with the check receipts and the review decision as evidence. Returns `published`, `rework{reference}` or `escalated`. |
| `aq.coding` (the default binding) | Runs attempt 0 (implementation), then up to `max_repairs` repair attempts (at most 8). Each repair attempt gets the failing evidence reference as its `context`. |

- **Evidence is invalidated by a subject change.** Each attempt prepares a new candidate and re-runs every check on it. Publish carries only that attempt's receipts and review.
- **Review never substitutes for a check.** Checks run before review. A failed check sends the run to rework without a review.
- **Explicit refusals:**
  - `build()` refuses when the implementer and reviewer families are the same (compared trimmed and case-insensitively).
  - It refuses more than 8 repairs, more than 32 checks, or duplicate check ids.
  - Every unexpected outcome routes to `escalated`.
- `CodingPolicy::project_default(checks)` is anthropic implementer, openai reviewer, 2 repairs.
- `input(&CodingRequest)` builds per-attempt logical keys `{key}/a{i}/work` and `{key}/a{i}/review`, so retries are idempotent.

### Artifact API (`crates/aq-server/src/playbooks/artifacts.rs`)

| function | behavior |
|---|---|
| `validate(registry, bytes)` | `Artifact::from_canonical_bytes` checks canonical form, structure and digest (≤1 MiB). Every command and event must exactly equal the owner's pinned catalog contract. |
| `install(op_id, bytes)` | Validates the bytes and installs them. Content-addressed and idempotent. |
| `activate(op_id, binding, digest)` | Activates the artifact for the binding and records the previously active artifact. |
| `rollback(op_id, binding)` | Re-activates the previous entry on the activation stack (activate pushes, rollback pops). With nothing to roll back to, it refuses with `Conflict`. |
| `install_coding_default(op_id, policy)` | Installs the four coding artifacts and activates `aq.coding`, each under a derived operation id. |

- **Idempotent operation ids:** a replay with the same request returns the record with `duplicate: true`. Reusing an id for a different request returns `Conflict`.
- **Activation affects only new runs.** The engine pins each run's artifact at admission.
- **Ledger:** the `Ledger` trait has two implementations:
  - `MemoryLedger`, used by the tests;
  - `PgLedger`, backed by migration `0084_playbook_activations.sql` (`PK(namespace_id, op_id)`, with `seq` ordering).
- **Catalog:** the `Catalog` trait is implemented by `DriverCatalog`. Activation runs under an active grant (`Service::active_authority`). The new `Driver::binding_artifact` method returns the binding's current artifact.

### Owner routes (`api.rs`, owner-only, body limit 2 MiB)

- `POST /api/playbooks/artifacts/validate` `{artifact}`
- `POST /api/playbooks/artifacts` `{op_id, artifact}`
- `POST /api/playbooks/bindings/{binding}/activate` `{op_id, artifact, grant_id, grant_revision}`
- `POST /api/playbooks/bindings/{binding}/rollback` `{op_id, grant_id, grant_revision}`
- `POST /api/playbooks/coding/default` `{op_id, policy, grant_id, grant_revision}`

No CLI entry was added. The CLI belongs to F7.

## Verification

Commands, run from the worktree with `export PATH=$HOME/.cargo/bin:$PATH`, `RUST_TEST_THREADS=2` and `CARGO_BUILD_JOBS=2`:

```
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked --workspace coding_policy_review_rejection_creates_rework_attempt
cargo test --locked --workspace activation_switches_future_runs_only
```

- `coding_policy_review_rejection_creates_rework_attempt`:
  - The fake Host7 peer returns `changes_requested` on the first review.
  - Asserts `work.ensure` kinds `[implementation, review, repair, review]`, and that the repair's context is the review reference `aq.review.decision/r1`.
  - Asserts the review is cross-family (`reviewer_family=openai`) and the checks re-run on the new candidate.
  - Asserts a single publish with evidence `[check-receipt:2, aq.review.decision/r2]`.
- `activation_switches_future_runs_only`:
  - Installs A and B through the API.
  - Run 1 is admitted on A, B is activated, run 2 is admitted on B, rollback restores A, and run 3 is admitted on A.
  - After settling, the root runs are pinned to A, B and A in catalog-revision order, and all of them published.
  - The `act-b` replay is a duplicate and leaves the current artifact at A. Reusing it with a different request returns `Conflict`. A second rollback returns `Conflict`.
- These tests need no database, no daemon and no sleeps. Each runs in about a second.

Environment: WSL2 Linux, stable Rust from `$HOME/.cargo/bin`.

## Limits (follow-up tasks filed)

- **D3 settlement is not replaced.** `profiled_execution/settlement/default_policy.rs` (`aq.default-completion.v1`) remains the automatic-settlement policy. D9 makes `aq.coding` the playbook-binding default through `install_coding_default`, but it does not reroute D3 settlement. That needs the D5–D8 runtime. Follow-up filed.
- **Human decision is omitted.** `decision.request` is not in the Host7 grant, so the policy has no human decision step. Review never stands in for one, and nothing auto-approves.
- **Check source comes from the run input.** The `candidate.prepare` output has no source OID, so the check source is taken from the run input.
- **Real Host7 `work.ensure` does not complete runs yet.** It returns `ensured` with no completion, so the policy escalates until D5–D8 emit `aq.operation.updated` / `completed`.
- **PgLedger has no DB test yet.** Concurrent activations on the same binding are serialized only by the engine. Ledger concurrency hardening is filed as a follow-up.
- **Install ledger rows are informational.** Install is content-addressed in the engine.
