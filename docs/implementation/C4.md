## What changed

### Template allowlist and activation pin (`crates/aq-server/src/templates.rs`)
- Server config `[templates] allowlist = "<path>"` is read once at startup.
  - The file is the C3b allowlist JSON: `schema_version: 1`, `entries[]` of `name`, `version`, `image_digest = "sha256:<64 lowercase hex>"`.
  - Limits: at most 1 MiB and 1024 entries. Names and versions are 1–128 characters with no `@` and no control characters.
  - Provenance fields are ignored.
- `POST /api/profiles/catalogs/activate` resolves every `Execution.environments` entry before opening the transaction.
  - An entry resolves as `name@version` exactly, or as a bare `name`.
  - Duplicate entries that name the same digest are not ambiguous.
  - Zero matches refuses with 409 `environment_template_missing`. More than one digest refuses with 409 `environment_template_ambiguous`.
  - A refused activation writes nothing: no revision change and no pin rows.
- On success, the pins are stored in `profile_catalog_environment_templates` (keyed by catalog digest and environment) in the activation transaction. They are also returned as `environment_templates` in the activation receipt.
- Arbitrary images are never accepted. With no `[templates]` configured, nothing is pinned, and every B1-registered sandbox node refuses with `environment_template_unresolved`. Host-native nodes are unchanged.
- Digest pin in the frozen LaunchManifest: no new manifest field. Selection requires the selected `InstalledHarness.environment.digest` to equal the pinned template digest. That digest is already frozen in the manifest's environment `ArtifactRef`.

### Migration 0055 (`0055_environment_templates.sql`; state format 54 → 55)
- `profile_catalog_environment_templates(catalog_digest → profile_catalog_artifacts, environment, template_digest hex)`.

### Selection placement facts (`crates/aq-selection/src/placement.rs`)
- `SelectionInputs.placement: Option<Placement>` uses serde default and is omitted when `None`, so legacy inputs still deserialize.
- `Placement` is checked in `candidate_core` after freshness. Checks run in this order, and the first failure becomes the `CandidateTrace.reason_codes` entry:
  1. node ceiling (Unavailable):
     - `node_concurrency_ceiling_reached`
     - `node_spend_ceiling_reached`
     - `node_spend_unaccounted`
  2. preference hold (Unavailable): `placement_preferred_backend_available`
  3. `required_backend_capability_unsupported` (Unsupported)
  4. `environment_template_unresolved`
  5. `environment_template_digest_mismatch`
  6. `template_not_advertised`
  7. `template_missing_selected_harness_version`: the template's advertised harnesses must contain the selected harness's exact `cli_version`.
- A missing capability or template is always a typed refusal. Nothing degrades to a lesser backend or image.
- Input bounds are added to `validate.rs`.

### Server placement facts (`crates/aq-server/src/profiled_execution/placement.rs`)
- `facts` is called by the intelligence resolver. It returns `None` for a node with no `delegated_node_boots` registration, which is a host-native node.
- For a registered node, it builds `Placement` from the authenticated B1 `BackendAdvertisement`:
  - capabilities and templates
  - the catalog's stored pins
  - `ceiling(adv, active, spend)`:
    - concurrency: active `holds_task` attempts ≥ `max_concurrent_sandboxes`
    - spend: a configured spend ceiling with no comparable accounted spend refuses as `node_spend_unaccounted`. Spend is `None` until H2.
  - `preferred_peer`
- Preference:
  - The default is `[docker-local, boat, cloudflare-containers]`. `ProjectPolicy.placement = {preference, required_capabilities}` overrides it.
  - Policy validation requires distinct kinds, at most 3 kinds and at most 4 capabilities.
  - Unlisted kinds rank last.
- A lower-preference node gets no offer while some higher-ranked peer is eligible. A peer is eligible when it is registered, has an unexpired `intelligence_node_snapshots` snapshot, is under its ceilings, has the required capabilities and advertises the pinned template.
- The hold is bounded: it ends at the latest when that peer's snapshot expires.
- The hold is explained by the `placement_preferred_backend_available` trace reason.
- The scan covers at most 256 peers.

## Limits
- Spend: H2 is out of scope. A node that advertises a spend ceiling is refused with `node_spend_unaccounted` until accounted spend is fed in (`calm-delta-18.6.1`).
- Placement is evaluated at selection (the resolver) only. Grant and launch fences do not re-derive it (`calm-delta-18.6.2`).
- Peer eligibility checks the pinned template, but not the peer's harness CLI version for the specific candidate. A peer advertising the template with a different harness version can still cause a hold until its snapshot expires.
- Sandbox nodes must report `InstalledHarness.environment.digest` as the template image digest. This is filed as a CROSS-REPO FOLLOW-UP (aq-worker) comment on `calm-delta-18.6`.
- The B1 wire schema, B5a, C5a1 and C5b are untouched.
- Design-doc updates (config, reason codes, table) are proposed in `calm-delta-18.6.3`. `docs/architecture` and `docs/specs` are not edited here.
