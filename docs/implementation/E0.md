The scenario creates its own Compose project, state, secrets, database volume,
random loopback ports and bare Git repository. It asserts all four services are
healthy and server dependency reports are ready. It seeds through public APIs,
replays the seed with identical IDs and revision 1, rejects changed inputs,
checks the graph task and Git binding, and verifies exactly one enrolled node.
It kills the serving aq-git engine, observes degraded readiness and a different
supervised process returning to ready without restarting the server. Graph
outage similarly degrades readiness and recovers. Owned containers and volumes
are removed before PASS is emitted. No owner repository is contacted.

The pinned Git service forks a guard and an engine. Killing the guard alone
originally left its engine serving, which correctly failed outage acceptance.
The supervisor now cleans the process group if its guard exits; the acceptance
crash targets the actual serving engine and lets its guard reap helpers and
close its incarnation. Whole-container/guard loss may retain a recovery fence;
automatic fence clearance is intentionally absent and is not qualified here.
