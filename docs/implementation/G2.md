## Delivered boundary

The G1 action union now registers eleven typed kinds. Each has its own strict
payload schema, request fixture and owner-only bootstrap capability, named
`<kind>@1`.

- **Graph node and edge commands** (`src/agent_access/human/graph_actions.rs`):
  - `task.edit`, `task.reprioritize`, `task.dependency.add` and `task.dependency.remove`
  - `knowledge.author`, `knowledge.correct`, `knowledge.verify`, `knowledge.retire` and `knowledge.restore`
  - Each command rereads the subject from Graph before it dispatches. A stale
    `expected_version` returns `conflict`, with `current_versions` set to the
    live version, and nothing is posted.
  - Each command posts one Graph mutation under the idempotency key
    `aq-dashboard-action:{operation_id}`.
  - Follow-up `steady-cascade-45.3.1` retains the exact native request before
    posting and reconciles unresolved operations by replaying those bytes under
    the same key and Graph identity; see the recovery boundary below.
  - Graph 2xx with matching results gives `confirmed`, with a `graph_change_set`
    receipt and the exact new revisions. Graph 409 gives `conflict`.
    400/403/404/422 give `rejected`. Anything else gives `unknown`.
- **B3 and B4 owners** (`src/agent_access/human/task_execution.rs`):
  - `task.cancel` and `task.retry` call these owners and never write Graph task
    lifecycle.
  - **Cancel** records a B3 native cancellation for the attempt that holds the
    task. It requires a `reason`. When no attempt holds the task, cancel is
    `rejected`. `confirmed` means only that the cancellation was admitted.
  - **Retry** runs `replacement::assess_task`, and only an admissible `Replace`
    goes on to `replacement::release`. The receipt is
    `replacement_release(<predecessor attempt>)`, after which the scheduler
    starts the replacement attempt. An unsettled, exhausted or non-active task
    is `rejected`. Retry never resets the retry, spend or sandbox budgets.
- **Operation conflicts:** a conflict outcome carries `current_versions`, which
  is serialized only on conflicts. Any other outcome that carries versions is
  treated as unproven and becomes `unknown`.
- **Contract files:**
  - The schema, README, fixtures and `check.py` are in
    `protocol/dashboard-actions/v1/`.
  - The schema digest pins are in the results-feedback and dashboard-read
    compatibility fixtures.
  - The schema digest is
    `sha256:9086d523fe3dd1ce7295b476938d59c2de4dfc701359be343ace100d66192641`.

## `aq:priority` agreement (for F2)

- `task.reprioritize` writes Graph metadata `aq:priority`, as a JSON integer in
  `-1_000_000..=1_000_000`.
- The producer reads it with `as_i64()`, sorts in descending order, and treats a
  missing or non-integer value as 0 (`profiled_execution/producer/workflow.rs:238-250`).
- A Graph metadata patch replaces the whole object, so the command reads the
  live metadata and sends it back with only `aq:priority` changed. The test
  `task_reprioritize_preserves_other_metadata` covers this.

## Limitations and follow-ups

- **Recovery uses idempotent POST replay:** Graph v1 has no mutation-receipt GET
  by key. `GET /changesets/{id}` returns a draft, and is not a mutation receipt
  lookup. Operation lookup can therefore send the original native request again.
  Graph returns the original committed result for the matching key and payload;
  this is the same logical operation, not a newly constructed mutation.
- **Older unresolved operations:** rows admitted before the native journal was
  introduced have no exact posted body. They remain unresolved; recovery never
  reconstructs their intent from current Graph content.
- **Dependency edits have a pre-dispatch window:**
  - Structural edges reject revision pins. The task version is checked before
    dispatch, but the `add_edge` mutation itself does not pin it.
  - Graph has no edge GET endpoint, so `remove_edge` relies on Graph's own
    `expected_version` check rather than a pre-read.
- **Response parsing:** the shared mutation transport now uses the existing
  duplicate-safe Graph parser, which permits finite fractional metadata and
  rejects duplicate keys, excessive JSON depth and nonfinite numbers. Response
  schema validation still applies. Integer-only `StrictValue` remains at the
  agent request/canonical-hash boundary. Native Graph bodies use ordinary JSON
  serialization so reprioritizing preserves fractional metadata as well.
- **Retry with no release:** when B4 assesses `Replace` with no release needed
  (the predecessor already released the task), retry returns `confirmed` and
  writes nothing.
- **Graph administrator checks:** Graph enforces administrator-only verify and
  restore, and a refusal maps to `rejected` (`knowledge_verify_forbidden_is_rejected`).

## Durable recovery follow-up (`steady-cascade-45.3.1`)

Migration 56 adds `dashboard_graph_intents`, keyed by the admitted dashboard
operation ID. Before any native POST, it stores the exact posted bytes and
`aq-dashboard-action:{operation_id}` key, plus the original project revision,
binding, workspace and configured Graph service identity. Update, delete and
truncate are refused; intent is retained across process restarts. An ambiguous
intent insert never licenses a send. Admission and terminal receipts remain in
the existing dashboard operation journal.

The supervisor authorized identical-body replay in message
`msg-47792782a03d4319bd063b2adb3e7d2f` after checking the sibling Graph source:
`aq-graph/src/store.rs:631-676` checks a receipt before executing, locks and
rechecks the key, and commits state plus result and receipt atomically.
`receipt()` at lines 1637-1657 scopes the key by workspace, actor and operation
and refuses a different payload hash. This supports replaying a committed
request without a second logical write. Current Graph authority is still
checked before the receipt is returned.

Lookup rechecks the current owner and project access, pins the original service
identity (origin, actor and credential verifier) and project binding, then posts
the retained bytes with a bounded deadline. It does not rebuild metadata or
recheck an obsolete subject version before replay. A validated success confirms
the operation with its original `graph_change_set` receipt and affected versions.
Confirmed, conflicting and rejected operations never replay. A new rejection,
conflict, changed identity/binding, timeout or transport fault during recovery
leaves the operation `unknown`: it cannot prove an earlier POST did not commit.
An initial definitive rejection still settles as `rejected` normally.

The timeout acceptance fixture commits state and its key receipt, withholds the
first response, and advances Tokio's test clock past the production three-second
POST deadline. It then constructs a fresh router, changes live Graph content,
and looks up the operation. The exact body/key are replayed and lookup confirms
with the original receipt/version; only one logical mutation commits. No real
sleep or real Graph service is required.
