## Delivered boundary

The G1 action union now registers eleven typed kinds. Each has its own strict
payload schema, request fixture and owner-only bootstrap capability, named
`<kind>@1`.

- **Graph node and edge commands** (`src/agent_access/human/graph_actions.rs`):
  - `task.edit`, `task.reprioritize`, `task.dependency.add` and `task.dependency.remove`
  - `knowledge.author`, `knowledge.correct`, `knowledge.verify`, `knowledge.retire` and `knowledge.restore`
  - Each command rereads the subject from Graph before it dispatches. A stale
    `expected_version` returns `conflict`, with `current_versions` set to the
    live version, and nothing is posted.
  - Each command posts one Graph mutation under the idempotency key
    `aq-dashboard-action:{operation_id}`.
  - Graph 2xx with matching results gives `confirmed`, with a `graph_change_set`
    receipt and the exact new revisions. Graph 409 gives `conflict`.
    400/403/404/422 give `rejected`. Anything else gives `unknown`.
- **B3 and B4 owners** (`src/agent_access/human/task_execution.rs`):
  - `task.cancel` and `task.retry` call these owners and never write Graph task
    lifecycle.
  - **Cancel** records a B3 native cancellation for the attempt that holds the
    task. It requires a `reason`. When no attempt holds the task, cancel is
    `rejected`. `confirmed` means only that the cancellation was admitted.
  - **Retry** runs `replacement::assess_task`, and only an admissible `Replace`
    goes on to `replacement::release`. The receipt is
    `replacement_release(<predecessor attempt>)`, after which the scheduler
    starts the replacement attempt. An unsettled, exhausted or non-active task
    is `rejected`. Retry never resets the retry, spend or sandbox budgets.
- **Operation conflicts:** a conflict outcome carries `current_versions`, which
  is serialized only on conflicts. Any other outcome that carries versions is
  treated as unproven and becomes `unknown`.
- **Contract files:**
  - The schema, README, fixtures and `check.py` are in
    `protocol/dashboard-actions/v1/`.
  - The schema digest pins are in the results-feedback and dashboard-read
    compatibility fixtures.
  - The schema digest is
    `sha256:9086d523fe3dd1ce7295b476938d59c2de4dfc701359be343ace100d66192641`.

## `aq:priority` agreement (for F2)

- `task.reprioritize` writes Graph metadata `aq:priority`, as a JSON integer in
  `-1_000_000..=1_000_000`.
- The producer reads it with `as_i64()`, sorts in descending order, and treats a
  missing or non-integer value as 0 (`profiled_execution/producer/workflow.rs:238-250`).
- A Graph metadata patch replaces the whole object, so the command reads the
  live metadata and sends it back with only `aq:priority` changed. The test
  `task_reprioritize_preserves_other_metadata` covers this.

## Limitations and follow-ups

- **No reconcile journal:** reconcile returns `None` for Graph commands, so an
  `unknown` Graph command cannot be reconciled through lookup without
  dispatching again. A durable Graph reconcile journal is follow-up `steady-cascade-45.3.1`.
- **Dependency edits have a pre-dispatch window:**
  - Structural edges reject revision pins. The task version is checked before
    dispatch, but the `add_edge` mutation itself does not pin it.
  - Graph has no edge GET endpoint, so `remove_edge` relies on Graph's own
    `expected_version` check rather than a pre-read.
- **Strict response parsing:** the shared settlement transport parses Graph
  mutation responses with `StrictValue`, which predates G2. That parser rejects
  non-integral numbers, so any echoed node with float metadata turns a
  successful write into `unknown`, and that outcome stays `unknown` until a
  reconcile journal exists. The fake Graph fixtures use integer metadata. This
  is recorded as a follow-up.
- **Retry with no release:** when B4 assesses `Replace` with no release needed
  (the predecessor already released the task), retry returns `confirmed` and
  writes nothing.
- **Graph administrator checks:** Graph enforces administrator-only verify and
  restore, and a refusal maps to `rejected` (`knowledge_verify_forbidden_is_rejected`).

What the two acceptance tests prove:

- **`knowledge_correct_with_stale_version_conflicts`:** the fake Graph holds the
  node at version 3 and the request expects version 2. The result is `conflict`
  with `current_versions == {"knowledge":"3"}` and recovery `refresh_and_review`,
  and no mutation is posted.
- **`task_retry_creates_replacement_attempt`:**
  - With an unsettled predecessor, retry is `rejected` and `holds_task` stays true.
  - After the predecessor finishes and its stop, retention and quiescent-effects
    receipts are present, retry is `confirmed` with a `replacement_release`
    receipt. One `profiled_replacement_releases` row exists, `holds_task` is
    false, and `assess_task` now returns `Replace` with no release needed, so
    the scheduler may start the replacement attempt.
  - Graph receives no writes.
