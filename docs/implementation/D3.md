# D3 automatic settlement and graph-event outbox consumer

Task: `crisp-meadow-36.4`. Plan: `docs/superpowers/plans/2026-11-03-d3-automatic-settlement.md`.
State format 55 (`crates/aq-server/migrations/0055_auto_settlement.sql`). It sits on top of
B4's formats 52 and 53 and H2's format 54. B4's replacement release stays a valid way to free the
claim: the two widened claim guards keep it and add the confirmed auto receipt.

## What ships

### Default completion policy (`settlement/default_policy.rs`)
A pure gate applies when the result review is the policy actor and the retained
definition body is exactly
`{"schema_version":1,"kind":"aq.default-completion.v1","delivery":"required"|"not_required"}`.
The gates run in this order, and the first one that fails decides:

1. **Acceptance.** The report must be the current head, carry a stop proof, and
   not be cancelled or superseded. A refused report goes to `rework` with reason
   `not_accepted`. If the stop proof is missing, the gate holds with
   `not_stopped`.
2. **Source retained.** The source must have an aq-git retention receipt
   (`source_retention::load_confirmed_locked`). Otherwise the gate holds with
   `source_not_retained`.
3. **Required checks.** Each required check needs a server-owned row in
   `profiled_check_evidence`, bound to (report, source digest, check id,
   validator digest).
   - Any failing check sends the task to `rework` with `required_check_failed`.
   - Any missing row holds the gate with `required_check_evidence_missing`.
   - The worker's report outcome and conclusion are never read as evidence.
4. **Delivery.** This gate only runs when delivery is required. It reads
   `profiled_delivery_evidence`: `published` passes, `unpublished` sends the
   task to `rework` with `delivery_unpublished`, `indeterminate` holds with
   `delivery_indeterminate`, and a missing row holds with
   `delivery_evidence_missing`.

### Automatic settlement (`settlement/automatic.rs`)
`results::record` records the report and then calls `settle_after_record`. A
settlement error is logged as `automatic settlement deferred` and never fails
the record.

Settlement takes a per-report advisory transaction lock and a row lock on
`profiled_auto_settlements`. The verdict is then applied:

- **Hold or rework.** The row is upserted with the evidence JSON: policy actor,
  policy, report, acceptance facts, source, each check with its validator digest
  and verdict, and delivery. Nothing is completed, and dependents are not
  released.
- **Complete.** The row is prepared with a version-checked graph `update_node`:
  - the expected version is the task version retained in the attempt's
    execution spec (`spec.task.version`);
  - the patch is `task_state=completed`;
  - the stable operation ID derives from `aq-auto-settlement-v1:{report}`;
  - the payload is at most 8192 bytes.

  The row is set to `possible` (`dispatch_count+1`) and committed before the
  POST.
  - A valid receipt sets `confirmed` and releases the attempt's task hold.
  - A 409 holds with `graph_version_conflict`. That row is never re-dispatched,
    so a conflict never overwrites.
  - Any other outcome leaves the row `possible`, and it is re-dispatched (at
    most 8 times) with the same operation ID.

A trigger enforces the owner identity (`aq.settlement-owner.auto.1`) on every
write. `settlement_claim_guard` and `profiled_historical_snapshot_guard` accept
a confirmed auto row as settlement. The replaced function bodies are attested by
`store/auto55.rs`. The earlier attestation layers (`settlement39`,
`never_granted40`) take the guard bodies from `replacement52::guard_overrides`,
which returns B4's bodies at format 52–54 and the D3 bodies at 55 and above.

### Graph-event outbox consumer (playbooks, profile `graph_events_v3`)
Catalog profile 3 is HumanReview2 plus the event contract
`aq.graph.operation.confirmed` v1:

- trusted producer `aq.graph.operations@1`;
- scope `project`;
- correlation `operation`;
- payload `{operation_id, task_id, attempt_id}`.

The config field `profile: "graph_events_v3"` selects it, and
`human_review_v2` is unchanged.

Each driver quantum calls `collect_graph_events(owner, 2)`. It seals at most 2
rows from `agent_graph_outbox` into `playbook_outbox` as `pending`, with:

- producer `aq.graph.operations@1`;
- epoch 0;
- `event_id` set to the graph outbox `event_id`.

The rows are selected under these rules:

- **Eligible:** the row is undelivered, its operation is `confirmed`, and its
  launch binding matches the namespace's project and workspace.
- **Order:** ascending `operation_seq`.
- **Skipped:** rows already sealed for this namespace.

`agent_graph_outbox.delivered=true` is set only inside `acknowledge_event`, in
the same transaction that records the engine's durable acceptance receipt. A
crash between the engine commit and the AQ ACK replays the same sealed event.
The engine then returns `duplicate` with the same key, which is
digest(producer, 0, event_id). The graph owner route and the rows are kept for
lookup and reconciliation.

The engine refuses events whose contract no installed artifact declares. The
driver therefore collects only after an artifact that declares this exact
contract has been installed. Runtime startup installs the configured
deployments, so production sets the flag at boot.

## Limits
- **Rework is recorded in AQ only.** The `rework` row carries the evidence and
  the reason. No graph mutation reopens or reroutes the task.
- **The effects ledger is not consulted** by the gate.
- **Concurrent re-dispatch has no lease.** It relies on the stable graph
  idempotency key and the per-report advisory lock.
- **The evidence tables have no production writers yet.**
  `profiled_check_evidence` and `profiled_delivery_evidence` are read here, and
  their writers are the D6 and D1 seams. Until those land, a policy with
  required checks or required delivery holds, which fails closed.
- **A version conflict needs a new report.** `graph_version_conflict` is
  terminal for that report's automatic settlement.
- **Delivery is per event, not per namespace.** With two `graph_events_v3`
  namespaces on one project, the first ACK marks the row delivered, and the
  second namespace no longer collects it.
- **Poison events stop the queue.** An event the engine refuses still stops the
  outbox page loop (existing driver behaviour). Collection is gated on an
  installed consumer so a graph event cannot cause it.

- The settlement architecture should describe the default completion policy
