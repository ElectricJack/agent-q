# Separately owned accepted preparation: candidate first slice

Default inactive. Migration030 is an unregistered candidate, after scoped-presence
029. Its manual-SQL tests do not qualify ordered installation or runtime adoption.
The server consumes the exact joint admission0.1.9 source; older phase archives and
module bytes remain unchanged. No new execution issuer or worker driver is added.

A protected `Definition` whose identity begins `aq.accepted-preparation-policy/`
contains a typed PolicyDefinition: exact contract/runtime/qualification artifacts,
PhasePolicy, qualified source profile and conservative logical disk bytes, and
nine distinct owning-domain references. Startup validation rejects malformed,
duplicate or unqualified entries. These are explicit operator qualification pins,
not physical capacity proof; synthetic test policies must never be represented as
production qualifications. Ordinary configurations have no new routes.

Only the authenticated worker listener can mount:

- POST `/v1/worker/profiled-v2/proposal`: ProposalRequest naming exact identity,
  binding and negotiation. The returned Proposal is derived from retained original
  offer/spec/selection/Graph provenance and actual pinned policy, not caller facts.
- POST `/v1/worker/profiled-v2/accept`: phase Document::Accept, with one physical
  `aq-delivery-nonce`. The immutable accepted receipt is wrapped in a newly sampled
  AcceptedDelivery. Changed operation bytes conflict; exact replay never rotates
  material or extends the lease.

Each request is bounded to128KiB and shares a two-request fail-fast admission gate;
two separate blocking material-read permits remain owned by actual blocking jobs
through cancellation. Routes use existing worker control-pool authentication.
Database waits have2s lock/3s statement bounds. Source/private-file I/O occurs
outside authority transactions and is followed by fresh locked ownership/time
checks. Existing control/auth/CSRF behavior remains in force on the human listener.

The original remaining/proposal window gates timely first issuance. The separately
requested ResourceHold.maximum_preparation_ms bounds the new no-launch phase,
further limited by configured policy and original inline retention. Original
proposal/source clocks and resource/reservation identities are retained unchanged.
MaterialLease is issued by the existing private-material owner. One transaction
retains the actual material lease/link, reserved journal, hot Preparing owner and
new immutable acceptance record. No installation or retention receipt is invented.

Proposal/request/receipt JSONB text bytes join existing material/receipt bytes under
the same global quota lock:64MiB/4096 material leases globally and4MiB/256 per node,
plus bounded retained proposal counts4096/256. Exact replay does not consume new
admission quota. Histories are not pruned. Both new tables may be absent only on a
supported older28/29 schema; partial tables, missing current tables or enabled v2
operations without them refuse. Final ordered030 installation remains separate.

Artifact, material and source reads use an opaque internal PreparationAuthority
with exact original receipt kind/digest and explicit Legacy or AcceptedV2 origin.
The new origin is never converted to a PreparationPlan. Reads remain scoped to
original retained artifacts/material/source, current node/boot/runtime/project,
current principal/configuration and cancellation state, and the accepted window.
Source reads still inspect the actual configured retention owner outside SQL;
historical source observation expiry is not fresh source eligibility for Grant.

Legacy initial Grant cannot consume this origin because no legacy accept receipt
is produced. No v2 execution route exists. Renewal, terminal closure and strict
fresh confirmation must later integrate explicit phase-aware historical grant
provenance. Expiry refuses retrieval/delivery but does not release holds, prove
physical stop or settle a task. Current NeverGranted refuses unsupported v2;
expired/unknown attempts stay held pending separately qualified recovery/closure.
Lost accepted responses may exact-replay while live; no automatic mutation retries,
new operation IDs, cleanup, provider calls or account rotation are performed.
