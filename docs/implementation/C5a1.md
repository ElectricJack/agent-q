## Delivered behavior

- `CredentialKind` is the closed `api-key` / `subscription-login` metadata enum;
  existing startup configurations default to `api-key`. Neither kind has special
  runtime behavior in this change.
- `CredentialConfig.allowed_backends` defaults to all supported backend kinds:
  `docker-local`, `boat`, `cloudflare-containers`. This is an unrestricted
  credential policy; placement independently controls which backends are enabled.
  Operators can narrow the list. Unknown values, duplicates, and lists longer than
  `BackendKind::ALL` are rejected. `allowed_node_ids` still applies.
  **An explicit `allowed_backends = []` is valid and means deny-all, whereas
  omitting the key means allow-all.** `load` logs a warning for an empty list.
- `load` copies that policy into `AuthorizedCredential` in canonical `Ord` order,
  so any spelling of the same set is the same policy. The nested credential
  policy in startup input must retain its default, preventing two policy knobs.
  The registry configuration digest is unchanged for default configurations:
  an `api-key` credential contributes the exact pre-C5a1 `(credential,
  allowed_node_ids)` tuple, a `subscription-login` credential adds its kind, and a
  narrowed allowlist participates only through the derived, skip-if-unrestricted
  `AuthorizedCredential.allowed_backends`. Upgrading with an unchanged legacy
  configuration therefore needs no revision bump and keeps in-flight preparations
  pinned to the stored digest valid. Changing kind or narrowing the allowlist is a
  configuration change and requires a newer registry configuration revision.
- `CapabilitySnapshot.backend_kind` is an explicit optional trusted fact. The
  selector denies a known backend outside the list with
  `credential_backend_not_allowed`; missing identity for a restricted credential
  yields `credential_backend_unknown`. Both use `PolicyDenied`, and existing
  explicit fallback policy governs any next candidate.
- Material provisioning and issuance independently check the same policy before
  reading private material. A selector result alone cannot bypass issuance policy.
- Default snapshots omit the new unrestricted/unknown values when serialized;
  the frozen pre-change task-selection input/output/error vectors still match.
  The central schema and normative examples include a narrowed policy and its
  explicit denial. Central selection has no backend identity and also fails closed
  for restricted credentials.

## Integration boundary

B1/C4 advertisement consumption is intentionally not implemented. Current server
inventory and issuance callers explicitly supply `None`, and `select_central`
hard-codes `backend_kind: None`. Thus existing defaults continue working, while
narrowed credentials fail closed until C4 supplies trusted backend facts at each
boundary. The new helper inputs are typed `Option<aq_selection::BackendKind>`; no
untrusted request hint is accepted here.

**Operator consequence until C4 lands:** narrowing a credential's
`allowed_backends` to anything other than the full set disables that credential
everywhere — for the central installation and for every runner — with
`PolicyDenied` / `credential_backend_unknown`. Narrowing is not yet a working
placement feature; it is a fail-closed contract that C4 will activate.

Observable reason codes are `credential_backend_not_allowed` (only once C4 supplies
a known backend) and `credential_backend_unknown` (today, for any narrowed
credential). `credential_backend_policy_invalid` is defense in depth only: startup
`validate` and `validate_installation` reject an invalid allowlist before
`candidate_core` evaluates policy, so it is not expected to be observed.

No permit binding, lineage fencing, concurrency limits, refresh/write-back,
enrollment, or runner credential installation was added. Tests use synthetic
material and PostgreSQL fixtures; they do not qualify real provider accounts or
container backend execution.
