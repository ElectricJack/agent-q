## Delivered behavior

- `CredentialKind` is the closed `api-key` / `subscription-login` metadata enum;
  existing startup configurations default to `api-key`. Neither kind has special
  runtime behavior in this change.
- `CredentialConfig.allowed_backends` defaults to all supported backend kinds:
  `docker-local`, `boat`, `cloudflare-containers`. This is an unrestricted
  credential policy; placement independently controls which backends are enabled.
  Operators can narrow the list. Empty denies all. Unknown values, duplicates,
  and lists longer than three are rejected. `allowed_node_ids` still applies.
- `load` copies that policy into `AuthorizedCredential`. The nested credential
  policy in startup input must retain its default, preventing two policy knobs.
  Both kind and backend allowlist participate in the registry configuration digest.
  A change requires a newer registry configuration revision. Existing installations
  adopting this digest format must also advance their configuration revision.
- `CapabilitySnapshot.backend_kind` is an explicit optional trusted fact. The
  selector denies a known backend outside the list with
  `credential_backend_not_allowed`; missing identity for a restricted credential
  yields `credential_backend_unknown`. Both use `PolicyDenied`, and existing
  explicit fallback policy governs any next candidate.
- Material provisioning and issuance independently check the same policy before
  reading private material. A selector result alone cannot bypass issuance policy.
- Default snapshots omit the new unrestricted/unknown values when serialized;
  the frozen pre-change task-selection input/output/error vectors still match.
  The central schema and normative examples include a narrowed policy and its
  explicit denial. Central selection has no backend identity and also fails closed
  for restricted credentials.

## Integration boundary

B1/C4 advertisement consumption is intentionally not implemented. Current server
inventory and issuance callers explicitly supply `None`. Thus existing defaults
continue working, while narrowed credentials fail closed until C4 supplies trusted
backend facts at each boundary. The new helper inputs are typed
`Option<aq_selection::BackendKind>`; no untrusted request hint is accepted here.

No permit binding, lineage fencing, concurrency limits, refresh/write-back,
enrollment, or runner credential installation was added. Tests use synthetic
material and PostgreSQL fixtures; they do not qualify real provider accounts or
container backend execution.
